The harness model

An AI tells you “done.” Only two things can be wrong with a done: it’s the wrong thing — you were misunderstood — or it’s the right thing, built wrong — it doesn’t match what was agreed.
There is no third way to fail a request — every bug, every disappointment is one of these wearing a costume.
Software is a controlled disc inside a drifting world; meaning must cross two membranes to get in — one membrane per failure. Three actors: one wants, one crosses, one watches. From that loop we derive the stabilizers that keep judgment affordable — and the watcher exists only until the membranes stop lying.

1a · Tower of abstraction, read as history — every translator was once human

Story. Machines ate the tower bottom-up; each conquered hop deleted its judge. AI is the newest wave — climbing the top two.

Every earlier automation arrived already proven — a compiler that mis-compiles is a bug, not a coin-flip, so its judge was deleted on arrival. The AI wave is the first to land on the top two hops still stochastic: same input, different output, no proof. We took the human out without the machine being proven — so the deleted judge must be rebuilt by hand, around an unproven translator. That rebuilding is harness engineering.

Frame. Only the top two hops are probabilistic — the harness exists for those two arrows.

✓ the three who replaced them
AGENT (LLM)crosses · both hops

The new translator. Does both hand-labor jobs — but unproven.

  • stateless — starts blank every run→ give it memory: specs, checkpoint history, and harness records as external state
  • forward-only, no built-in verdict — can't feel when it's wrong→ build programmatic sensors: tests, drift checks, lint sense right/wrong for it
  • fully programmable — total control of its inputs, tools, loop→ sandboxes, fixed entrypoints, MCP — make it reliably do what no employee would
  • stochastic — same input, different output→ keep the judge; wrap the unproven hops in disciplines
  • cheap & parallel — no fatigue, fans out→ afford exhaustive interviewing, many drafts, broad review
INTENT HOLDERwants · never crosses

What's left of the human after the agent took the labor — the irreducible wanting.

  • holds tacit intent — knows the want, can't fully state it→ exhaustive interviewing, recommend + veto pulls it out
  • the living reference (hop 1) — only they can confirm "that's what I meant"→ their sign-off is the verdict; the written spec makes it transferable after
  • drifts — the want changes over time→ durable record freezes intent at decision time
  • scarce attention — won't read everything→ keep the work legible and small
JUDGEwatches · contingent

The two reviewers, merged into one watcher — now judging machine output, not human.

  • contingent — exists only because the translator is unproven→ drive stochasticity to zero and it deletes itself, like the lower tower did
  • judges machine output now — new failure modes: fluent, confident, wrong→ adversarial checks, not trust
  • expensive — burns human attention→ legible work + tests (judgment pre-paid) keep it affordable
  • transferable — once a spec exists, any spec-reader can judge→ the record moves the verdict off the one head

No skill was lost — the four split three ways: the doing went to the AGENT, the checking to the JUDGE, the wanting & authority to the INTENT HOLDER. What didn't transfer — memory, built-in judgment, steady intent — is exactly what the levers rebuild.

Entrypoints

→ predictable world

The only allowed ways to start the system — each a complete, valid configuration.

→ predictable world — the launch conditions, pinned

The product of harness engineering is the software — so the ways to start it must be as controlled as the software itself. A small, fixed set of doors; everything else is sealed.

  • Minimal & complete — pnpm dev starts the usable app; Playwright starts its own isolated browser/API/database stack.
  • Proxy is explicit — Vite proxies /api to Express; tests set a per-run DB path and API port.
  • Count stays small — app, API-only, build, unit/API tests, browser tests, demo scripts, and harness setup.
  • Not listed = doesn't exist — specs/harness.md is the command registry; shared automation uses those commands.

e.g. pnpm dev · pnpm test · pnpm build · pnpm test:e2e

Encoded workflows

→ the membranes

The rules as a runnable graph — a crossing's process can't be skipped.

→ the membranes — the crossing process, guarded

A crossing is reliable only if the process is. We encode the rules as a runnable graph (Archon), so the discipline can't be skipped under deadline.

  • Harness before edits — agents read the repo's command and layering contract first.
  • Diff classification — changes are routed as UI, API, persistence, slide-content, demos, specs, or harness.
  • Validation map — the workflow chooses from pnpm test, pnpm build, pnpm test:e2e, and demo scripts.
  • Advisory only — the workflow recommends; registered commands remain the proof.

e.g. /change-check → .archon/workflows/change-check.yaml

System of records

→ durable record

Meaning that drifts is pinned in writing — in stores both readers can use.

→ durable record — meaning pinned in writing

Drift is the enemy. Every concept has one written home, shaped so the human judge and the agent can both read it.

  • Specs are the source — README.md, PLAN.md, and specs/harness.md define the app and harness.
  • Shared contract — shared/api.ts is the client/server shape boundary.
  • Data in one sink — SQLite stores presentations, groups, slides, themes, and ordering.
  • Agent memory — Entire checkpoints capture session history when the CLI is installed.

e.g. API tests prove repository/service behavior; Playwright proves browser deck flows.

The work is shaped so a reviewer (human or agent) can hold one unit in their head. Three layers + a body-shape rule.

One connected graph

→ the directionnot built yet

The limit of durable record + no-duplicate-concepts: specs and code as graphs over the same concept nodes, connected.

→ the direction — one canonical source of truth

Most data and relationships are graphs. Represent specs and code as graphs over shared concept nodes, connect them, and have agents + humans work the substrate — not scattered files.

  • One substrate — spec-graph ⇄ code-graph over the same concepts; specs / code / traces / learnings become views of it, not separate stores.
  • Drift becomes a query — a spec node with no binding edge = unbuilt; a code node with no spec edge = undocumented drift. check_spec_drift = diff the graphs.
  • Duplicates surface mechanically — two nodes for one concept = the no-duplicate-concepts violation, found by the graph, not by review.
  • Membranes are edge ops — elicitation makes spec nodes, binding makes code edges; both readers (judge + agent) traverse one queryable thing.

seed: future code graph over shared/, server/, and src/ — nodes = routes, services, repositories, components, slides, and shared API types.
